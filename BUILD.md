# Building

Use Windows x64, Visual Studio 2022 with the C++ desktop workload and Windows SDK, CMake 3.25 or newer, and Git. Release builds use the dynamic MSVC runtime.

Check out [RE-UE4SS](https://github.com/UE4SS-RE/RE-UE4SS) at `97b7e501c19d8b2b7c662feee73aaa0dc1f0a4d1`, with recursive submodules. Its Unreal dependency must be at `eb40a05f49509bdeb1ac39287032b60af585cca8`. The CMake configuration checks these source revisions. MinHook and the SDK's header dependencies are pinned in `native/CMakeLists.txt`.

From an x64 Native Tools command prompt:

```bat
cmake -S native -B build -A x64 -DUE4SS_SDK=C:/src/RE-UE4SS
cmake --build build --config Release
cd build
cpack -C Release -G ZIP
```

The DLL is `build/Release/main.dll`. The archive is `build/Style-Without-Sacrifice.zip`. Its explicit installation list includes the native DLL, Lua settings adapter, mod metadata and logos, player documentation and license notices. It excludes personal settings and saved outfits.

`native/UE4SS.def` lists the host exports needed to link this implementation. Building the SDK itself is not required. The running UE4SS installation must supply the imported exports and declared C++ interfaces. Do not substitute an import library from an unrelated SDK revision.

The clothing hook identifies the specific accessor's instructions in executable memory. Reflected row structure and slot checks protect the data handed back to the game. A changed accessor disables that hook and reports the missing capability. No game version string or whole-file hash is used as a runtime gate.

Hidden wrist rows explicitly set the reflected `AppearanceMesh.GauntletIndex` byte to zero, matching the game's unoccupied wrist slot. The native row constructor's value of 255 is passed directly to arm deformation when the wrist slot has a row. Missing or changed field metadata leaves that slot's equipped look in place; other appearances remain available.

Catalog processing is incremental; appearance work follows inventory and player events. The native UI is built from the game's loaded widget classes. Game assets are loaded from the installed game and are not redistributed.

Weapon sizing resolves the selected appearance's item and loads its soft `WeaponBlueprint` class reference through `LoadClassAsset_Blocking.AssetClass`. The reference is copied into owned call parameters; a hard class reference is also supported. It reads `RelativeScale3D` from the class default object's `BaseMesh` template, preserving the selected weapon's authored size. The game's `GetSheathedWeaponScale` can reduce greatswords and is not used for transmog sizing. Class-loader, object-reference and double-vector layouts are checked before use. The demo greatsword and sacrificial knife resolve sizing from their matching stock items. Fourteen identified catalog-only rows use unit scale; failure to load any other item keeps the equipped appearance instead of guessing unit scale. Inherited template scales are preserved, including the Blood Slave sword at 1.2 and Uriash's sword at 1.8. The resulting owned scale is cached with the choice and applied to drawn weapons, sheathed weapons, scabbards and character previews through `SetRelativeScale3D`. Scale restoration is conditional on the installed mesh and scale still matching; shared item assets and class defaults are never modified.

The `[DB] Heavy Weapon` correction resolves `BP_Weapon_Pickaxe` and reads both `StaticMesh` and `RelativeScale3D` from its `BaseMesh` template. Its stock appearance row contains a cart, while the separate PickaxeTest row contains an axe, so neither row supplies the corrected mesh. The template is validated before use; unavailable class, mesh or scale keeps the equipped appearance. This look has no scabbard. Preparation uses the existing choice cache and adds no recurring work.

Drawn targets must belong to the player or preview and have the reflected `EWeaponType::Sword` classification. The combat enum groups physical weapons under Sword; Fist and Claw actors are excluded before retention and again before applying a mesh. Missing classification leaves drawn appearances unchanged while preserving other slots. Ownership accepts the player or preview actor directly, or the reflected owner of `OwningCombatComponent`. `GetMainWeapon` is validated as a zero-input hard-object getter and queried during an appearance refresh to recover actors created before attachment. No global weapon search or idle polling is used.

Weapon completion follows the game's `OnWeaponAppearanceSet` event after combat ownership, item data and mesh initialization. The existing script callback accepts the named wrapper or the exact reflected event-graph entry, with deletion-aware graph references and a bounded registry. Other graph entries do not trigger cosmetic work. Repeated completion events coalesce; callbacks during a refresh are consumed by its final weapon pass.

The game defers character appearance work beyond `OnInventoryContentsChanged`. A separate native completion listener runs after mesh/clothing updates and notification delivery. Its entire completion body, exact exception-table boundary and three linked instruction sequences are checked in executable memory, with relative addresses relocated. A missing or ambiguous contract disables only this listener and reports the unavailable recovery capability. The listener filters the player and preview on the game thread, queues a cosmetic reapplication without another game rebuild, and permits failed selected-weapon preparation to retry at this readiness event. Successful preparations remain cached. Logging records selected row/scale, failed capabilities and aggregate completion counts; detailed logging defaults off.

Transmog leaves drawn and sheathed weapon visibility under game control, so retained inactive actors remain hidden. The fixed weapon list reuses deleted or no-longer-owned slots. Visibility restoration for Hide/scabbards requires the installed mesh still to match. Player teardown and rebinding restore surviving edits before clearing caches; ClientRestart also resets context when the same pawn is reused across saves. Preview teardown precedes rebinding. Loader-thread shutdown only discards records and does not call into gameplay.

Hard object parameters use the property's copy operation. The SDK's legacy `SetObjectPropertyValue` wrapper has no mapping in its UE5.5 virtual table definitions, even when the host exports the wrapper. The Wardrobe page is a native panel in the existing hub widget tree; hub activation and tab rebuilding drive its setup. Attachment exceptions consume the same finite retry budget as missing data, and other failed actions cancel their pending work.

Menu opening uses `UIFrontend.GetFrontend` to resolve the local player's active UI. Blueprint lifecycle bindings handle both direct events and their optimized event-graph calls. Graph targets and entry offsets come from the loaded functions, with a validated integer `EntryPoint` parameter; no fixed Blueprint offsets are assumed.

The source license is MIT. Preserve the bundled dependency notices when distributing binaries. The UE4SS SDK's MIT license is included under `LICENSES`.

## Engine controller input

Controller events enter through the device-aware `FSlateApplication` implementation of `FGenericApplicationMessageHandler::OnControllerAnalog`, `OnControllerButtonPressed` and `OnControllerButtonReleased`, before Slate/CommonUI can consume them. The current Slate application is identified through the registered SetFocusToGameViewport accessor and its image-bounded global. Wardrobe reads the three device-aware entries from that instance's secondary message-handler table. Each target must be an executable function entry, with the eight-byte FName, device argument, handler adjustment and typed fifth argument validated. Changed argument or object layouts disable capture with a specific reason. Whole controller bodies, exact function lengths, device-mapper internals and downstream dispatch/focus implementations are not compatibility gates: the game owns and executes that code. Readable registration data may span multiple memory-protection regions. No game version, storefront or whole-image hash enables or rejects the hooks. Keyboard/mouse remain available when a required controller capability is unavailable.

Reflected input-device ownership and connection metadata are validated; enum metadata and object references are deletion-aware. The active frontend GameMenuLayer must contain the hub and its Wardrobe page must be selected. Only the higher MenuLayer, ModalLayer, GameMenuTutorialLayer and PhotoModeLayer block input. GameplayDialogueLayer and TutorialLayer precede the game menu in the frontend overlay. PhotoModeLayer follows the whole root overlay in its parent. The two lower layers may keep active widgets while the hub is open and must not block navigation. Missing ownership capabilities are distinct from a known modal blocker. Keyboard/mouse retain their foreground fallback only for unavailable capabilities.

Button gesture ownership survives page/focus transitions: stock presses retain stock releases, while captured presses do not leak releases. Entering capture neutralizes previously forwarded axes. Observed neutral axes are retained across tab entry and foreground return, including for drivers that emit only changed values. Held or unknown axes still require neutral before navigation; disconnection invalidates their history. Re-entering capture clears stale action-axis samples so neutral is not required twice. Up to four device gesture records are retained; unused records are preferred, and only meaningful input changes the active navigation device. Cancellation clears pending reset/save holds and stick repeats. Stock bumpers continue to reach hub tab handling.

Hooks filter the setup/game thread and guard reentrancy. Teardown disables hooks and drains callbacks before object-lifetime tracking is removed. The module and at most three published trampolines stay resident until process exit so a late entry can forward safely. Hot reload is not supported; restart the game after replacing the DLL. Never-enabled partial installations remove their hooks normally.

Logging defaults to Warning, with Off/Error/Warning/Info/Debug levels. Debug alone enables controller summaries, limited to one per ten seconds of active menu work, with ownership status and event, device-change, reflected-query and enum-cache counters. No per-event log formatting is performed when disabled. A successful UI-ownership check makes seven bounded reflected queries, and each retained connected device uses two queries per visible-menu sample. These are operation bounds, not frame-rate measurements.

Offline checks cover production event state/callbacks, downstream gesture balance, persistent lower HUD layers, higher modal blockers, first-movement and no-click navigation, schema/focus failures, disconnect/owner reuse, multiple devices, partial hook installation and teardown, plus ABI-negative and unrelated-code-positive contracts, split registration regions, and real MinHook operations on a disposable mapped executable. They do not establish live native DualSense compatibility or in-game performance. The UI continues to use the game's Xbox glyph assets for every controller. Previous/Next show R_Up/R_Down and use the right-stick Y axis, with one action per tilt and hysteresis. That axis shares neutral-entry, focus, device and downstream-drain handling with the existing axes; its digital direction companions are consumed without duplicate page actions. Page shortcuts are ignored in outfit dialogs and consume simultaneous grid/confirm input, including at page boundaries.
